# 評価ハーネス（フレームワークなし／ありの NG判定通過率）

`cases/` のテストケースを複数の LLM に解かせ、別の LLM（ジャッジ）に採点させて、「`dist/lite.md` を読み込ませると NG判定の通過率がどう変わるか」を再現できる形で計測する。結果は `cases/results/<日付>-<短いID>/` に残し、README や記事に実測値として載せる。

## セットアップ

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install -r scripts/eval/requirements.txt   # anthropic SDK のみ（OpenAI は標準ライブラリで呼ぶ）
export ANTHROPIC_API_KEY=...   # 未設定なら Claude の被評価モデルはスキップ（ジャッジが Claude なら実行不可）
export OPENAI_API_KEY=...      # 未設定なら OpenAI の被評価モデルはスキップ
```

`--dry-run` と単体テストは SDK もキーも不要。

## 使い方

```sh
# 1. API を呼ばずに、読み込んだケースと組み立てたメッセージ・ジャッジ入力・費用見積もりを確認する
python3 scripts/eval/run_eval.py --dry-run [--verbose]

# 2. ジャッジの自己テスト: 既知の不合格例（各ケースの「ありがちな回答」・空の応答・「わかりません」）を採点させ、
#    すべて不合格にできるかを確かめる。被評価モデルは呼ばない
python3 scripts/eval/run_eval.py --judge-selftest

# 3. 少数で試す
python3 scripts/eval/run_eval.py --cases 01,07 --trials 1

# 4. 本番（既定: 全11ケース × 既定モデル × 2条件 × 3試行）
python3 scripts/eval/run_eval.py --models claude-opus-5-5,gpt-5 --trials 3 --workers 4

# 5. ジャッジを別系統に替えて再採点し、結論が変わらないかを確かめる
python3 scripts/eval/run_eval.py --judge-model gpt-5 ...
```

主な引数（既定値は `run_eval.py` 冒頭の `DEFAULTS` に集約）:

| 引数 | 既定 | 内容 |
| --- | --- | --- |
| `--models` | `claude-opus-5-5,gpt-5`（環境変数 `EVAL_MODELS`） | 被評価モデル。`anthropic:ID` / `openai:ID` で provider を明示できる。OpenAI の ID は実行前に公式のモデル一覧で現行のものを確認する |
| `--judge-model` | `claude-opus-5-5`（環境変数 `EVAL_JUDGE_MODEL`） | ジャッジ。Anthropic と OpenAI のどちらも指定できる |
| `--judge-effort` | `high` | Anthropic ジャッジの effort |
| `--judge-repeats` | 1 | 同じ応答を何回採点するか。2以上で多数決（同数は不合格）とし、合否の一致率を出す |
| `--conditions` | `baseline,framework` | 片方だけも可 |
| `--framework-mode` | `two-turn` | 下記「条件」 |
| `--cases` | 全件 | `01,07` / `1-3` |
| `--trials` | 3 | ケース×モデル×条件ごとの試行回数 |
| `--workers` | 4 | 並列数。429 が多ければ下げる |
| `--temperature` / `--effort` / `--reasoning-effort` | 送らない | 指定したときだけ API に送る。記録は `summary.md` と `run.json` |

## 条件

- **baseline**: 質問だけを1通送る。
- **framework**（`--framework-mode` で渡し方を選ぶ）
  - `two-turn`（既定）: `lite.md` → 定型の受け答え「前提を読み込みました。まず、家を買おうと思ったきっかけを教えてください」 → 質問。実際の使い方を再現しつつ、2通目のぶれを排除する。受け答えは `lite.md` 自身が指示している1文。
  - `two-turn-live`: 上の受け答えも実際にモデルに生成させる（呼び出しが1.5倍になる）。生成された受け答えは `transcripts.jsonl` の `ack_generated` に残る。
  - `inline`: `lite.md` と質問を同じ最初のメッセージに入れる（`lite.md` は「相談内容が一緒に書かれていれば、そのまま答えてください」と指示している）。

試行の実行順は固定シードでシャッフルし、条件ごとに時間帯や混雑の偏りが出ないようにしている。`lite.md` を含むメッセージには Anthropic のプロンプトキャッシュを付ける（出力には影響しない。費用だけが下がる）。

## 採点

ジャッジには**質問と回答本文だけ**を渡し、条件（フレームワークあり/なし）もモデル名も渡さない。採点表は、ケースの「NG判定」と `cases/README.md` の「全ケース共通のNG判定」、「期待する回答の要点」。判定方針の全文は [`judge_prompt.md`](judge_prompt.md)。要点は次のとおり。

- **確認質問だけの回答も合格になり得る。** フレームワークありの AI は、結論を出す前に売却時期やきっかけを1つずつ確認するのが期待動作。1ターン目が確認質問だけでも、それが期待する要点（例: 売却時期を聞く）に沿っていれば合格とする。要点と無関係な確認質問だけなら不合格。
- **NG判定は意味で判定する。** 「『売却時期』という言葉が出てこない」は語句一致ではなく、何年住むか・いつ売るかに触れているかで判定する。
- **条件つきの NG は前段の行為があるときだけ評価する。** 「〜だけで結論を出す」は、結論を出していない回答には該当しない。
- **共通NG「確認事項を一度に全部並べて聞く」** は、独立した確認項目を3つ以上一度に答えさせている場合に該当とする（基準の置き方は「限界」を参照）。
- 職種としての専門家（不動産エージェント・FP・税理士）への相談の勧めは共通NGに当たらない。特定の会社・サービス・このリポジトリ・SNS 共有を勧めた場合に当たる。
- 長さや丁寧さでは評価しない。
- 各項目に、判定理由と**回答からの逐語引用**を付けさせる。引用が回答に実在するかはハーネス側で機械的に確認し、実在率を `summary.md` に出す。
- 出力は構造化出力（JSON スキーマ、項目 ID は enum で固定）。全項目が1回ずつ判定されていなければ1回だけ採点し直し、それでも欠ければ採点エラーとして記録する。

### 合格の定義

- **合格** = NG判定（共通＋ケース固有）に1つも該当しない、かつ応答が空・拒否・無関係でない、かつ（確認質問だけの応答なら）要点のどれかに沿っている。
- **要点充足率（厳格）** = met=1、partial=0.5、deferred=0 の平均。**（寛容）** は deferred（前提となる確認質問をして適切に後回し）も1と数える。条件つきでまだ条件が現れていない要点（not_applicable）は分母から除く。1ターン目の評価なので、フレームワークありは厳格では低く、寛容では高く出やすい。両方を見る。
- 参考値として、**共通NGを除いた合格率**も出す。どの種類の NG が合格率を動かしているかを切り分けるため。

### 採点に回さないもの

API エラー（再試行しても失敗）、出力上限での打ち切り、モデルの拒否、要求と異なるモデルが応答した場合は、不合格に混ぜず `errors.jsonl` と `summary.md` の件数欄に分けて記録する。

## 出力（`cases/results/<YYYY-MM-DD>-<6桁ID>/`）

| ファイル | 内容 |
| --- | --- |
| `summary.md` | モデル×条件の合格率（95%区間）、framework − baseline の差、ケース別の表、よく該当した NG、ジャッジの信頼性の目安、トークン使用量。実行日時・ジャッジ・試行回数・`lite.md` のコミットハッシュと sha256・`judge_prompt.md` の sha256 も載る |
| `transcripts.jsonl` | 1試行1行。送ったメッセージ（`lite.md` 本文は `{{dist/lite.md sha256=...}}` に置換）、サンプリング条件、応答本文、stop_reason、応答したモデル名、トークン数、再試行回数、所要秒数 |
| `judgements.json` | 項目ごとの判定・理由・引用・引用の実在確認、合否 |
| `errors.jsonl` | 採点に回らなかった試行と、その分類 |
| `run.json` | 引数を含む実行設定の全体、SDK の版、git の状態 |

### 区間の出し方

同じケースの試行どうしは相関するので、二項分布の区間（Wilson など）は狭く出すぎる。合格率と、framework − baseline の差（同じケースで対応づけた差）は、**ケース単位のクラスター・ブートストラップ**（2,000回、固定シード）で 95% 区間を出す。ケースが11件なので区間は広い。差の区間が 0 をまたぐなら「差があるとは言えない」と書く。

## 推奨手順（記事に載せる前に）

1. `--dry-run` でケースの読み込みとメッセージを確認する。
2. `--judge-selftest` で、既知の不合格例がすべて不合格になることを確かめる（緩すぎるジャッジの検出）。
3. `--trials 1` で一度回し、`judgements.json` の不合格のうち数件と合格のうち数件を**人が読んで**判定に同意できるか確かめる。同意できない判定が1割を超えるなら、`judge_prompt.md` を直してから本番を回す。
4. 本番を回す。可能なら `--judge-repeats 3` か、別系統のジャッジでの再採点も行い、結論が変わらないことを確かめる。
5. 記事には合格率だけでなく、区間・ジャッジのモデル・試行回数・`lite.md` のコミット・実行日を一緒に載せる（`summary.md` の「実行条件」表をそのまま使える）。

## 費用の目安

`--dry-run` の最後に、文字数からの概算（1文字≒1トークン、出力は被評価モデル3,000・ジャッジ6,000トークンと仮定）を表示する。既定設定（11ケース×2モデル×2条件×3試行）では、被評価モデル132回・ジャッジ132回で、入力約130万トークン・出力約120万トークン。Claude Opus 5.5 をジャッジにした場合、ジャッジ分だけで約20ドル（キャッシュ割引前）。実行後は API が返したトークン数で実測値を表示する。

## 限界

- **ジャッジの偏り。** LLM ジャッジは、自分と同系統のモデルの回答を好む傾向（自己選好）、長い回答を好む傾向がある。ジャッジが被評価モデルに含まれる場合は `summary.md` に警告を出す。別系統のジャッジでの再採点と、人手ラベルとの一致率の確認で補う。人手ラベルとの一致率はこのハーネスでは測っていない。
- **単発（1ターン目）の評価である。** フレームワークは複数ターンで確認を重ねて結論に至る設計なので、1ターン目では計算や結論の要点が出ない。要点充足率（厳格）は構造的に低く出る。逆に、2ターン目以降で誤った結論を出す失敗はこの評価では捕まえられない。
- **判定基準の解釈が入る。** 「確認事項を一度に全部並べて聞く」の「全部」を「3つ以上」と置いた、確認質問だけの応答を合格とし得る、など、`judge_prompt.md` の方針次第で数値は動く。`judge_prompt.md` を変えた前後の結果は比較しない（sha256 で区別できる）。
- **モデルの版で結果が変わる。** 同じモデル ID でも提供側の更新で挙動が変わりうる。実行日とモデル ID、応答したモデル名（`served_model`）を必ず併記する。
- **サンプリング条件は各 API の既定値。** Claude Opus 5.5 などは temperature の既定値以外を受け付けないため、既定では送らず、ばらつきは試行回数で捉える。
- **ケース数が少ない。** 11件のため区間が広く、ケースの作り方（`cases/` の要点・NG判定はこのフレームワークの作成者が書いている）に結果が依存する。フレームワークありが有利になる観点で書かれていること自体が偏りになりうる。
- **ラベルの漏れ。** フレームワークありの回答は「前提に従い」などと書くことがあり、ジャッジが条件を推測できてしまう場合がある。

## 開発

```sh
python3 -m unittest discover -s scripts/tests   # API 不要
```

- ケースのパースと採点ルールは `case_parser.py`（SDK 非依存）、API 呼び出しと集計は `run_eval.py`。
- Anthropic は公式 Python SDK（`requirements.txt` で版を固定）、OpenAI は Chat Completions を標準ライブラリで呼ぶ。SDK の自動再試行は切り、429・5xx・接続エラーはハーネス側でジッター付き指数バックオフ（`retry-after` を優先）で再試行し、回数を記録する。
- 被評価モデルにはサーバー側の拒否フォールバック（別モデルへの切り替え）を付けない。別モデルの応答を採点すると、指定したモデルの評価にならないため。
